# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Scheduling app for a public-health screening programme (*lịch khám sức khỏe toàn dân*): an admin opens individual work days, departments are rotated onto them, each department fills in who it is sending plus a contact phone, and every work day gets a work report with roll-call and signatures. **All user-facing strings — including API error messages thrown from the worker — are Vietnamese.** Keep new messages Vietnamese.

The repo history starts as a hospital duty-roster app (`lich-truc`); branch `lich-ksktd` is the pivot to this domain. Anything still mentioning `staff`, `duty`, `leave`, `schedule_units` or week-based scheduling is leftover from that app.

```bash

```

Full local stack = `npm run dev` **and** `npm run worker:dev` together; the frontend has no API without the worker.

Single test / single case:

```bash
npx vitest run tests/schedule.test.ts
npx vitest run -t "tua khám"
npx vitest tests/schedule.test.ts     # watch mode
```

There is no linter or formatter. `npm run build` is the typecheck gate (`noEmit: true`, `strict: true`).

`src/worker/env.d.ts` is generated by Wrangler — never hand-edit it.

## Architecture

Three layers, deliberately few files:

- `src/shared/` — types and **all business rules**, imported by both the worker and the React app so validation runs identically on each side. `schedule.ts` holds date/month/rotation math; `validation.ts` holds permission and input rules.
- `src/worker/index.ts` — one Cloudflare Worker: non-`/api/*` requests go to the `ASSETS` binding (SPA), `/api/*` goes through `routeApi`, a flat ordered chain of `path`/`method` checks. Errors are thrown as `HttpError(status, vietnameseMessage)` and caught in `fetch`.
- `src/app/` — React 19 SPA. `App.tsx` is the shell (login, month navigation, tabs, notifications, swap-accept screen); views live in `ScheduleView.tsx`, `ScheduleTools.tsx` (work days, per-position rotation dialog, sections/positions manager), `AdminViews.tsx` (departments, users, history, settings, profile) and `ReportView.tsx`. Shared bits: `common.tsx`, `scheduleExport.ts` (PNG/Excel), `reportWordExport.ts` (docx+jszip), `lunar.ts`.

A Postgres client is created **per request** in `fetch` (`createPostgresClient` → `connect` → `end`), routed through Cloudflare Hyperdrive.

**Hyperdrive query caching must stay disabled** (`wrangler hyperdrive update <id> --caching-disabled`). It is on by default with a 60s TTL and this app reads back its own writes in the same request (every mutating endpoint returns a fresh list), so caching makes the UI look like nothing saved — and it also caches the session lookup.

## Database: D1-shaped SQL running on PostgreSQL

This is the single most important thing to know. The worker was written against Cloudflare D1 and still speaks D1's API; `src/worker/database.ts` is a shim that translates to `pg`:

- Query style stays `env.DB.prepare(sql).bind(...).first() / .all() / .run()`, and `env.DB.batch([...])` wraps statements in `BEGIN`/`COMMIT`/`ROLLBACK`. Write new code in this style.
- SQL uses `?` placeholders; `postgresSql()` rewrites them to `$1, $2, …` (quote-aware). Do not write `$1` yourself.
- `.run()` on an `INSERT` appends `RETURNING id` to get `meta.last_row_id`, but **only for tables listed in the `identityTables` set** in `database.ts`. Add any new identity-PK table there or `last_row_id` will be `null`.
- Booleans are `SMALLINT` `0`/`1` in the schema (`active = 1`, `present = 0`), not Postgres `boolean`. Row mappers coerce with `!!row.x`.
- `pg` type parsers are overridden so `DATE` stays a `YYYY-MM-DD` string and timestamps serialize predictably — dates flow through the whole app as ISO strings, never `Date` objects.
- Schema lives in the `lich_ksktd` Postgres schema; `search_path` is set on the DB role, not by the worker.

**Schema source of truth is `postgres/schema.sql`**, applied manually — there is no migration runner. The old app's D1/SQLite `migrations/` directory and its D1→Postgres import script were deleted with the pivot; don't reintroduce that pattern. `scripts/create-admin.mjs` seeds the first admin (its password hashing must stay identical to `hashPassword` in the worker).

## Testing pattern

Route handlers are not integration-tested. Instead, SQL/logic fragments are **exported as pure functions from `src/worker/index.ts`** (`assignmentPersonUpdate`, `clearScheduleStatement`, `rotationDepartmentLookup`, `rotationMembersInsert`, `passwordResetSessionCleanup`, `usernameAvailabilityLookup`) and asserted in `tests/database.test.ts` — returning `{ sql, bindings }` shapes, or checking placeholder counts to prove a batch was collapsed into one statement. Transaction and `RETURNING id` behaviour is tested by passing a fake `{ query }` object to `new PostgresDatabase(client as never)`. When adding non-trivial worker SQL, extract it the same way rather than trying to boot a worker.

`src/shared/` is covered directly by `tests/schedule.test.ts` and `tests/validation.test.ts`.

## Domain rules worth knowing before editing

- **Work days are the calendar.** `work_days` (date PK + `session` = `morning`/`afternoon`/`full`) is what the schedule is built from; not every day is a work day. The schedule table is **week-based** (`GET /api/schedule?weekStart=YYYY-MM-DD`, Monday-normalised) so it never exceeds 7 columns; only work days inside that week become columns. The response also carries `monthWorkDays` (with `assignmentCount`) for the month-wide "Ngày làm việc" manager, and `month`, derived by `monthOfWeek()` = the month of the week's **Thursday**, so a week straddling two months is filed under whichever month holds most of it. `assignments.date` and `work_reports.date` reference `work_days(date)` with `ON DELETE CASCADE`, so deleting a work day deletes its assignments and report.
- **Rows.** Row 1 is the coordinator row (`coordinator_assignments`, admin-assigned only). Below it, rows are **examination positions** (`positions`, e.g. "Khám nội") grouped under user-defined `sections`. Both are admin-only, managed from the Cấu hình page. A cell holds any number of departments (`assignments`, unique per position+date+department), each carrying the person name + phone the department fills in.
- **Rotation is per position** — one `rotations` row per position, its turns in `rotation_members`. A turn may contain several departments, all of which stand at that position that day. `rotationTurnIndex(workDays, date, startDate, turnCount)` advances per **work day**, not per calendar day. `POST /api/rotations/:positionId/apply` and `POST /api/rotations/apply` (every enabled position) take an explicit `{ from, to }` range and re-attach any person name/phone already filled for the same position+date+department.
  **The turn index must be computed over every work day from `startDate`, then filtered to the applied range** — `applyRotation` loads `listWorkDays(min(startDate, from), to)` for exactly this reason. Passing only the range's work days makes each week restart at turn 1; there is a regression test for it ("giữ đúng nhịp tua khi chỉ áp cho một tuần").
- **Who may edit what**: `canManageSchedule(role)` (admin | dieu_phoi) gates scheduling; `requireAdmin` gates departments, users, settings **and the coordinator row**. Coordinators change their own days only through the swap-request flow (`swap_requests`, token-based, needs the other coordinator's consent) — that is why they cannot assign the coordinator row directly.
- **Person edit window**: departments edit their own cell while `date >= today`; the `lock_person_on_workday` setting tightens it to `date > today`. Enforced in three places that must stay in sync — `canEditPersonOnDate`, `canEditAssignmentPerson`, and the SQL predicate built by `assignmentPersonUpdate`.
- **Reports**: only a scheduler creates/edits the numbers; attendance and signatures are keyed by **assignment** (`work_report_attendance.assignment_id`) because one department can stand at several positions on the same day; the coordinator assigned that day (or admin) signs off on `work_reports`. After that signature only admin can still edit.
- **Audit log is global**, not scoped to the viewed period: `listAuditLogs(env, filters)` takes no date range, orders newest-first and caps at 300 rows. `GET /api/audit` accepts only the `actor`/`action`/`q` filters, `DELETE /api/audit` wipes the whole table (admin only), and `getSchedule` embeds the same global list. A `khoa_phong` user still only sees their own rows via `auditFiltersForUser`.
- Dates/times are handled in `Asia/Ho_Chi_Minh` (`APP_TIME_ZONE`, `todayInVietnam`) while raw date arithmetic runs in UTC on ISO strings.

## Frontend detail

`styles.css` styles bare `input`/`select`/`textarea` with `width: 100%; min-height: 44px; border...`, which also hits checkboxes and radios. The reset in the appended block at the end of the file fixes that — keep it, or every new checkbox renders as a full-width white box.

The schedule grid has a variable number of columns. `ScheduleView` sets `--day-count` on `.schedule-table-wrap`; the CSS block appended at the end of `styles.css` derives `grid-template-columns` and `min-width` from it for both `.schedule-grid` and `.section-label`. Earlier rules in that file still hard-code 7 columns — the appended block overrides them, so keep new grid rules after it.

## Build quirk

`vite.config.ts` pins the entry to `assets/index.js` and then copies it over two legacy hashed filenames (`index-dw1Yt5pg.js`, `index-VcWkZwT2.js`) so browsers holding a cached `index.html` keep working. Don't remove that plugin or rename the entry without knowing those stale references are gone.

## Secrets

`wrangler.jsonc` holds the Hyperdrive binding id only. The Postgres connection string never goes in source or config: `wrangler hyperdrive create` for production, `.dev.vars` (gitignored) for local.
